# 자율형(Hermes류) 에이전트로의 전환 로드맵

2026-08-31, "Claude + Human-in-the-loop"와 "Hermes 같은 자율형 Agent"를
비교하는 표를 계기로 정리했다. 이 3-Role 구조(운영자·모니터·자동 해결자 +
코디네이터)가 자율형 실행에 얼마나 가까운지, 무엇이 남았는지 기록해 둔다.

## 비교표

| 구분 | Claude + Human-in-the-loop (일반형) | 지금 이 프로젝트(voc-avatar-partner) | 자율형(Hermes류)으로 가려면 | Claude Code에 실제로 있는 도구 |
|---|---|---|---|---|
| 작업 시작 | 사람이 지시 | 사람이 코디네이터 세션을 열고 `@voc-avatar-operator` 호출 | 트리거 기반 시작(주기적으로 "새 VoC 있나" 확인) | `schedule` 스킬(cron 기반 예약 실행) 또는 `/loop`(자율 페이싱 반복) |
| 계획 수립 | Claude 제안 → 사람 확인 가능 | 이미 Claude가 제안 → 사람 확인 없이도 진행(2026-08-31, 발송 승인 게이트 제거) | (이미 충족) | — |
| 코드 수정 | 중간 승인/확인 빈번 | 리졸버가 자체적으로 fix→PR, 승인 대기는 PR merge뿐(GitHub 리뷰) | (이미 상당 부분 충족) | — |
| 테스트 실패 | 결과 보고 → 사람이 다음 지시 | 재시도 없이 그대로 보고 → 사람이 다음 지시(`voc-avatar-monitor.md` §4) | 오류 유형별 자동 재시도/우회 정책 | 규칙만 있으면 구현 가능 — 지금은 **의도적으로** 재시도 안 함(구조화된 오류를 조용히 삼키지 않기 위해) |
| 도구 호출 | permission/승인 개입 가능 | 세션 permission 모드에 따라 다름 — "Allowed by auto mode classifier"로 이미 일부 자동 통과 중 | 사전 허용 도구 목록으로 완전 무프롬프트 | `update-config`/`fewer-permission-prompts` 스킬로 `settings.json` allowlist 구성 |

| 종료 | 사람이 결과 확인 | 사람이 "다 됐다"고 판단 | 명시적 종료 조건("배정 목록이 비었으면 종료") | 로직만 추가하면 됨(간단) |
| 장시간 작업 | 사람과 interactive session 중심 | 코디네이터 = 대화형 세션(사람이 열어야 함) | unattended/background 실행 | `schedule` 스킬 — Claude Code 세션 자체를 cron으로 무인 실행 가능 |

## 결론 — 진짜 병목은 "코디네이터가 대화형 세션이라는 것"

운영자·모니터·자동 해결자 서브에이전트 자체는 이미 자율형에 가깝게
설계돼 있다(발송 승인 게이트도 2026-08-31에 없앴다). 진짜 막힌 지점은
**"서브에이전트 간 연동은 오직 코디네이터를 통해서만"이라는 원칙**
(`README.md` §7)이고, 지금 코디네이터가 사람이 매번 여는 대화형 메인
세션이라는 것이다. `schedule` 스킬로 cron 예약 실행되는 무인 세션으로
바꾸면, 그 세션 자체가 "사람 없이 주기적으로 깨어나 목록 확인 → 3-Role
호출 → 종료"하는 코디네이터 역할을 대신할 수 있다 — **3-Role 구조나
파일들을 바꾸지 않고, 코디네이터의 "실행 방식"만 바꾸는 것**이다.

## 의도적으로 남겨두는 것: "애매한 경우 사람에게 escalation"

이건 제약이 아니라, 이번 프로젝트 내내 만든 안전장치들(선례 재확인,
근거 파일 인용, 자기 사실 지어내기 금지, `evidence` 필드 기록 등)이
실패했을 때의 **최후 방어선**이다. 발송 승인은 없앴지만, "판단 자체가
애매할 때 멈추고 묻는다"까지 없애면 뭔가 잘못됐을 때 아무도 모르게
계속 진행된다 — Hermes 표의 "정책 범위 내 자동 수행"이 안전하려면 그
"정책"이 지금 이 시스템보다 훨씬 정교해야 한다. 그래서 무인 코디네이터를
만들 때도, human-in-the-loop 상황(운영자 §4, 리졸버 §7)은 실행을 멈추고
다음 예약 실행 때 사람의 답을 확인하는 방식으로 유지한다 — 차단하되
비동기로 만드는 것이지, 없애는 게 아니다.

## 무인 코디네이터 구현 — `schedule`(클라우드)이 아니라 `/loop`(로컬)

처음엔 `schedule` 스킬(cron 기반 **클라우드** 에이전트)로 만들려고 했으나,
시도해보니 근본적으로 안 맞았다: `schedule`이 만드는 라우틴은 Anthropic
클라우드의 격리된 CCR 세션에서 도는데, 이 파이프라인 전체가 로컬 전용
리소스에 의존한다 — fake VoC Hub/Agent Factory 서버(`127.0.0.1:9090`),
로컬 설치된 `@voc-avatar-*` 서브에이전트(세션 스냅샷 기반 인식),
`~/.voc-hub/` 아래 파일들, `AGENT_FACTORY_API_KEY` 환경변수. 클라우드
세션은 이 중 무엇에도 닿을 수 없어 첫 단계(모니터에게 목록 요청)부터
실패한다.

그래서 **로컬에서 계속 도는 프로세스**가 필요하고, `/loop` 스킬
(`ScheduleWakeup` 기반, 지금 이 대화와 같은 로컬 세션)이 이 조건을
만족한다 — 로컬 리소스에 그대로 접근하면서 지정한 간격마다 스스로
깨어나 프롬프트를 재실행한다. 코디네이터 역할을 이 로컬 루프가 대신
맡고, 매 실행마다:

1. 모니터에게 배정 목록(§1) 요청
2. 목록이 비어 있으면 그대로 종료(다음 예약 실행을 기다림)
3. 각 건에 대해 운영자 1차 라우팅 → (필요시) 자동 해결자 위임/재확인 →
   운영자 2차 확정 → 모니터 발송까지 자동 진행
4. human-in-the-loop이 필요한 건은 그 건만 보류하고 다음 건으로 넘어감 —
   전체 실행을 막지 않는다
5. 처리 결과(voc_number별 decision, 발송 여부, 보류 사유)를 요약해 남기고
   다음 예약 시각까지 대기

**전제조건**: 이 방식은 로컬 Claude Code 세션(터미널)이 계속 떠 있어야
동작한다 — 세션을 닫으면 루프도 멈춘다. `schedule`처럼 세션을 완전히
안 열어놔도 되는 무인 실행은 아니고, "사람이 열어야 하는 대화형 세션"을
"열어만 두면 알아서 도는 세션"으로 바꾸는 수준의 자동화다.
